# Test All

프로젝트에 준비된 전체 테스트를 실행하고 결과를 확인한다.
테스트나 빌드가 실패하면 실패했다는 사실만 알리지 않고, 어떤 테스트에서 왜 실패했는지 원인을 분석해 해결 방법과 함께 쉽게 설명한다.

## 작업 절차

1. AGENTS.md와 프로젝트의 테스트 환경을 확인한다.
2. 프로젝트에 준비된 자동화 테스트를 모두 실행한다.
3. 프로젝트 빌드가 정상적으로 완료되는지 확인한다.
4. 테스트나 빌드에 실패하면 원인을 확인한다. → 아래 **실패 분석** 절차를 따른다.
5. 전체 결과를 정리하여 사용자에게 보고한다.

## 실행 기록

2~3단계를 진행하면서 다음을 기록해 둔다. 실패 분석과 결과 보고의 근거가 된다.

- 실행한 명령(또는 실행 방법)과 실행 위치
- 기준 커밋, 기존 미커밋 변경 여부, 실행 환경(OS, Node 버전)
- 각 명령의 종료 결과(성공 / 실패 / 중단 / 시간 초과)
- 실행된 테스트 수, 성공·실패·건너뜀 수 (도구가 알려주는 경우)
- 실패한 경우 출력된 오류 메시지와 로그

**건너뛴 테스트**는 이름과 이유를 기록하고, 그 범위를 "미검증"으로 보고한다. 이 프로젝트의 `tests/sprite-pipeline.test.mjs`는 Windows가 아니면 건너뛰므로, 다른 환경의 전체 통과에는 스프라이트 가공 검사가 포함되지 않는다.

자동 테스트는 Phaser 화면과 입력을 다루지 않는다. 화면 표시·입력은 이 스킬에서 확인하지 않으므로 결과에 "실제 화면 미확인"으로 적고, 확인이 필요하면 [UI 지침](../../../docs/ui/AGENTS.md)의 화면 확인 표(준비·입력·기대 화면)를 안내한다.

**테스트가 실행되지 않은 경우**도 따로 기록한다. 예를 들어 다음과 같은 경우다.
- 테스트 명령 자체가 실패했다. (도구 없음, 명령을 찾을 수 없음 등)
- 컴파일 오류 때문에 테스트가 시작되지 못했다.
- 테스트를 찾지 못했다. (0개 실행)
- 실행 중 중단되었거나 시간 초과로 끝났다.

이 경우 "테스트 실패"가 아니라 **"테스트 미실행"**으로 분류하고, 실행되지 못한 사실과 그 단계에서 나온 오류를 실패 분석 대상으로 삼는다.

## 실패 분석 (4단계 세부 절차)

**실패가 없으면 이 절차를 건너뛴다.** 경고나 사소한 출력을 분석 대상으로 만들어내지 않는다. 다만 결과에 영향을 줄 수 있는 경고(예: 건너뛴 테스트, 0개 실행)는 "발견한 문제"에 사실로만 적는다.

### 4-1. 실패 항목 나누기

실패를 다음 세 종류로 나누고 항목마다 번호를 붙인다.

| 종류 | 번호 | 대상 |
|---|---|---|
| 테스트 실패 | `T1`, `T2`… | 실행되었지만 실패한 개별 테스트 |
| 테스트 미실행 | `N1`, `N2`… | 실행되지 못한 테스트 실행 명령 또는 테스트 묶음 |
| 빌드 실패 | `B1`, `B2`… | 빌드 명령의 실패 (오류별로 나눌 수 있으면 나눈다) |

빌드 실패와 테스트 실패는 섞지 않고, 둘 다 아래의 같은 기준으로 분석한다.

### 4-2. 항목별 근거 수집

각 실패 항목마다 다음을 수집한다.

1. **실패 위치**: 실패한 테스트 이름과 테스트 파일 경로. 테스트 단위로 특정할 수 없으면 실패한 실행 명령.
2. **오류 메시지와 로그**: 실제 출력에서 원인과 관련된 부분을 **그대로 인용**한다. 전체 로그를 붙이지 말고, 오류 메시지와 그 앞뒤의 관련 줄(스택 트레이스의 프로젝트 코드 부분 등)만 발췌한다. 출력에 없는 내용을 오류 메시지처럼 쓰지 않는다.
3. **기대 결과와 실제 결과**: 로그(assert 메시지 등)나 테스트 코드에서 **확인할 수 있는 경우에만** 적는다. 확인할 수 없으면 "확인 불가"라고 적는다.
4. **관련 코드 위치**: 스택 트레이스나 오류 메시지가 가리키는 파일과 함수를 확인하고, 실제로 읽어본다.

### 4-3. 사실과 추정 구분

- **확인된 사실**: 로그, 오류 메시지, 코드에서 직접 확인한 것만 적는다.
- **추정 원인**: 사실로부터 추론한 원인이다. 반드시 "추정"으로 표시하고, 어떤 사실에 근거했는지 적는다.
- 원인을 정확히 알 수 없으면 추정이라고 밝히고, 가능한 원인이 여러 개면 가능성이 높은 순서로 나열한다.

### 4-4. 원인 분류

항목마다 다음 중 하나로 분류한다.

| 분류 | 기준 |
|---|---|
| **코드 문제** | 게임(제품) 코드의 동작이 기대와 달라서 실패했다. |
| **테스트 코드 문제** | 테스트의 기대값, 준비 과정, 정리 과정, 테스트 간 의존성 등 테스트 쪽이 잘못되었다. |
| **환경·설정 문제** | 도구·버전·의존성 누락, 경로, 권한, 설정 파일, 외부 리소스, 실행 환경 차이 때문에 실패했다. |
| **판단 불가** | 수집한 근거만으로 위 셋 중 하나를 고를 수 없다. |

- 분류는 근거가 있을 때만 정한다. 근거가 부족하면 판단 불가로 두고, 판단에 필요한 추가 정보를 적는다.
- 분류가 추정에 기반하면 "코드 문제(추정)"처럼 표시한다.

### 4-5. 여러 실패의 관계 판단

- 여러 실패가 같은 원인처럼 보여도 **근거 없이 하나로 묶지 않는다.** 항목은 각각 분석한다.
- 같은 오류 메시지, 같은 스택 위치, 같은 선행 실패 등 **공통 원인의 근거가 있을 때만** "T2, T3은 T1과 같은 원인일 가능성이 있음"처럼 관계를 적고, 그 근거를 함께 적는다.
- 빌드 실패나 미실행 때문에 이후 테스트가 실행되지 못했다면 그 연결 관계를 명시한다.

### 4-6. 해결 방법과 추가 확인 순서

- **해결 방법**: 무엇을 고치면 되는지 제안한다. 파일과 위치를 알 수 있으면 함께 적는다. 직접 수정하지 않는다.
- **추가 확인 순서**: 원인이 확정되지 않았다면, 원인을 좁히기 위해 확인할 것을 순서대로 적는다. (예: 해당 테스트만 단독 실행 → 특정 값 로그 확인 → 설정 파일 확인)
- **쉬운 설명**: 전문 용어를 줄이고, 무엇이 왜 실패했는지 한두 문장으로 풀어 쓴다.

## 테스트 결과 형식

### 테스트 결과
- 실행한 테스트 (실행한 명령, 실행 수)
- 성공한 테스트
- 실패한 테스트 (번호와 이름)
- 실행되지 않은 테스트 (있으면 이유와 함께)
- 건너뛴 테스트 (있으면)

### 빌드 결과
빌드 성공 여부와 발생한 오류를 설명한다.
빌드를 실행하지 못했다면 그 사실과 이유를 적는다.

### 발견한 문제
실패한 테스트나 추가 확인이 필요한 문제를 설명한다.
실패 항목은 아래 형식으로 적는다. 빌드 실패(`B`), 테스트 미실행(`N`), 테스트 실패(`T`) 순서로 적는다. 앞의 실패가 뒤의 실패 원인이 될 수 있기 때문이다.

```markdown
#### T1. <테스트 이름>

- **종류**: 테스트 실패 / 테스트 미실행 / 빌드 실패
- **위치**: `<테스트 파일 경로>` · `<테스트 이름>` (또는 실패한 실행 명령)
- **오류 메시지와 로그**:
  ```
  <실제 출력에서 발췌한 관련 부분>
  ```
- **기대 결과**: <확인한 내용 또는 "확인 불가">
- **실제 결과**: <확인한 내용 또는 "확인 불가">
- **확인된 사실**
  - <로그·코드에서 직접 확인한 것>
- **추정 원인** (추정)
  - <원인> — 근거: <어떤 사실에서 추론했는가>
- **원인 분류**: 코드 문제 / 테스트 코드 문제 / 환경·설정 문제 / 판단 불가 (추정이면 "(추정)" 표시)
- **다른 실패와의 관계**: <근거가 있는 경우만. 없으면 "확인된 관계 없음">
- **쉬운 설명**: <무엇이 왜 실패했는지 한두 문장>
- **해결 방법**: <제안>
- **추가 확인 순서**
  1. <먼저 확인할 것>
  2. <다음에 확인할 것>
```

실패가 없으면 이 섹션에 "실패한 테스트와 빌드 오류 없음"이라고 적고, 위 형식은 사용하지 않는다.

**축약형:** 실패·미실행이 없으면 보고 전체를 다음처럼 줄여 쓸 수 있다. 건너뜀과 미검증 범위는 생략하지 않는다.

```markdown
### 테스트 결과
- `<명령>`: <N>개 실행, 통과 <N>, 건너뜀 <K> (<건너뛴 테스트와 이유>)
### 빌드 결과
- `<명령>`: 성공
### 발견한 문제
실패한 테스트와 빌드 오류 없음. 미검증: <건너뛴 범위>, 실제 화면 미확인
### 최종 의견
<한두 문장>
```

### 최종 의견
프로젝트의 테스트 및 빌드 결과를 종합하여 설명한다.
실패가 있다면 먼저 확인할 항목 번호와, 원인이 확정된 항목과 추정 단계인 항목을 구분해 적는다.

## 규칙

- 테스트 과정에서 게임 코드를 임의로 수정하지 않는다.
- 실패한 테스트를 임의로 삭제하거나 건너뛰지 않는다.
- 실제로 실행하지 않은 테스트를 성공했다고 보고하지 않는다.
- 테스트 환경 문제와 코드 문제를 구분하여 설명한다.
- 문제가 발견되면 수정 방법을 제안하되 직접 수정하지 않는다.
- 테스트가 끝나면 사용자의 다음 지시를 기다린다.
- 테스트 코드도 직접 수정하지 않는다. 환경·설정 변경이 필요하면 제안만 한다.
- 원인을 정확히 알 수 없으면 추정이라고 밝힌다. 확인된 사실과 추정 원인을 섞지 않는다.
- 오류 메시지와 로그는 실제 출력을 그대로 인용한다.
- 여러 실패를 근거 없이 하나의 원인으로 단정하지 않는다.
- 실패가 없으면 원인 분석 대상을 만들어내지 않는다.
