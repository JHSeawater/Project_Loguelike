# Review Code

구현된 코드를 검토하고 문제점과 개선 방법을 제안한다.
문제를 발견하면 어떤 파일의 어느 부분에 문제가 있는지 파일 경로, 함수 이름, 코드 위치로 알려준다.

## 작업 절차

1. AGENTS.md와 사용자 요구사항을 확인한다. 루트 지침의 연결표로 관련 분야 지침도 읽는다. 구현 계획이 있으면 대상 계획서, 승인된 범위, 요구사항 ID(`R1`…) → 구현 단계 → 검증의 대응, 기준 커밋, 이전 검토에서 남은 문제를 함께 확인한다.
2. 구현된 코드와 관련 파일을 확인한다. 기준 커밋 이후의 변경(`git diff`)을 검토 범위로 삼고, 작업 전부터 있던 미커밋 변경은 구분한다.
3. 사용자 요구사항대로 기능이 구현되었는지 검토한다. 요구사항 ID가 있으면 ID별로 확인한다.
4. 버그가 발생할 수 있는 부분을 확인한다.
5. 기존 기능에 문제가 생길 가능성이 있는지 검토한다.
6. 발견한 문제와 개선 방법을 정리한다. 각 문제의 위치는 아래 **문제 위치 표기 규칙**에 따라 적는다.

## 문제 위치 표기 규칙

### 파일 경로와 함수 이름
- 파일 경로는 **프로젝트 루트 기준의 실제 경로**로 적는다. 파일 이름만 적지 않는다.
- 관련 함수·메서드는 가능하면 소속까지 적는다. (예: `PlayerController.HandleInput()`)
- 함수 밖의 코드(필드 선언, 전역 설정, 설정 파일 등)라면 그 사실과 대상 이름을 적는다. (예: `GameConfig` 클래스의 필드 `maxCount`)

### 줄번호
- 줄번호는 **현재 파일을 직접 읽어서 확인한 경우에만** 적는다.
- 검토 중 파일이 변경되었을 수 있거나 이전에 읽은 내용에 의존하고 있다면, 줄번호를 적기 전에 파일을 다시 확인한다.
- 줄번호를 추측하거나 대략적인 위치("~근처", "약 120줄")로 적지 않는다.
- 줄번호를 확인할 수 없으면 **"줄번호 확인 불가"라고 밝히고**, 함수 이름과 짧은 코드 구간으로 위치를 안내한다.

### 코드 구간
- 문제를 찾을 수 있는 **짧은 코드 구간**(보통 1~5줄)을 실제 코드 그대로 인용한다.
- 코드를 요약하거나 재구성해서 원문처럼 보이게 쓰지 않는다. 생략이 필요하면 `// ...`로 생략 위치를 표시한다.
- 줄번호를 적은 경우에도 코드 구간을 함께 적어, 파일이 바뀌어도 위치를 다시 찾을 수 있게 한다.

### 여러 파일이 연결된 문제
- 하나의 문제가 여러 파일에 걸쳐 있으면 **핵심 위치**와 **관련 위치**를 구분한다.
  - **핵심 위치**: 문제가 실제로 발생하거나 수정이 필요한 곳. 원칙적으로 하나를 고른다.
  - **관련 위치**: 문제를 유발하거나 영향을 받는 곳. (호출하는 쪽, 데이터를 넘겨주는 쪽, 같은 상태를 공유하는 쪽 등)
- 관련 위치마다 핵심 위치와 어떤 관계인지 한 줄로 적는다.

### 문제가 없을 때
- 발견한 문제가 없으면 **위치 정보를 만들지 않는다.** 문제 항목 형식을 빈 칸으로 채우거나, 예시용 위치를 적지 않는다.
- 대신 무엇을 검토했고(파일, 확인한 요구사항, 확인한 위험 범위) 그 결과 발견한 문제가 없다고 명확하게 설명한다.

## 검토 결과 형식

### 종합 평가
코드의 전반적인 상태를 간단히 설명한다.
검토한 파일과 범위를 함께 적는다.

### 발견한 문제
각 문제를 아래 형식으로 적는다. 중요도가 높은 순서로 정렬하고 `C1`, `C2`… 번호를 붙인다.

```markdown
#### C1. <문제 요약 한 줄>

- **중요도**: 높음 / 보통 / 낮음
- **핵심 위치**
  - 파일: `<프로젝트 루트 기준 경로>`
  - 함수/메서드: `<클래스.메서드()>`
  - 줄번호: <확인한 줄번호> 또는 "줄번호 확인 불가"
  - 코드:
    ```<언어>
    <문제를 찾을 수 있는 짧은 실제 코드 구간>
    ```
- **관련 위치** (여러 파일이 연결된 경우만)
  - `<경로>` · `<함수>` · <줄번호 또는 "확인 불가"> — <핵심 위치와의 관계>
- **문제 내용**: <무엇이 문제인가>
- **발생 조건**: <어떤 입력·상태·순서에서 문제가 생기는가>
- **실제 동작에 미치는 영향**: <사용자나 시스템에 어떤 결과가 나타나는가>
- **문제가 발생할 수 있는 이유**
  - 코드 근거: <코드의 어떤 부분이 왜 문제인가>
  - 요구사항 근거: <어떤 요구사항(ID가 있으면 ID)·지침과 어긋나는가. 요구사항과 무관한 일반 버그면 "해당 없음 — 일반 동작 오류"라고 적는다>
- **개선 제안**: <이 문제를 어떻게 고치면 좋은가>
```

발견한 문제가 없으면 이 섹션에 "발견한 문제 없음"이라고 적고, 위의 형식은 사용하지 않는다.

중요도 '낮음' 문제는 아래 축약형으로 적을 수 있다. 위치 표기 규칙(실제 경로, 확인한 줄번호, 실제 코드 인용)은 그대로 지킨다.

```markdown
#### C3. <문제 요약 한 줄> (낮음)
- 위치: `<경로>` · `<함수>` · <줄번호 또는 "줄번호 확인 불가"> — `<짧은 실제 코드>`
- 문제와 개선: <무엇이 문제이고 어떻게 고치면 되는가>
```

### 개선 제안
발견한 문제를 어떻게 해결하면 좋을지 설명한다.
문제별 개선 제안은 위 항목에 적고, 이 섹션에는 여러 문제를 함께 해결하는 방법, 수정 순서, 수정 시 주의할 점처럼 문제 하나에 묶이지 않는 내용을 적는다. 해당 내용이 없으면 "문제별 개선 제안 참고"라고 적는다.

### 최종 의견
추가 수정이 필요한지 판단한다.
수정이 필요하면 먼저 고쳐야 할 문제 번호를 적는다.
수정 후 다시 검증할 요구사항 ID와 테스트를 적어 다음 구현·검토에서 이어받을 수 있게 한다. 없으면 생략한다.

## 규칙

- 코드 검토 단계에서는 코드를 수정하지 않는다.
- 실제 코드와 사용자 요구사항을 근거로 검토한다.
- 확인하지 않은 문제를 사실처럼 설명하지 않는다.
- 사소한 코드 스타일보다 실제 동작에 영향을 주는 문제를 우선한다.
- 문제가 없다면 발견한 문제가 없다고 명확하게 설명한다.
- 검토가 끝나면 사용자의 다음 지시를 기다린다.
- 줄번호는 현재 파일에서 확인한 경우에만 적고 추측하지 않는다. 확인할 수 없으면 그 사실을 밝히고 함수 이름이나 코드 구간으로 안내한다.
- 코드 구간은 실제 코드를 그대로 인용한다.
- 문제가 없을 때는 위치 정보를 만들지 않는다.
