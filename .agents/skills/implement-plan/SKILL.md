# Implement Plan

작성된 구현 계획을 바탕으로 실제 코드를 작성한다.
각 단계가 끝날 때마다 완료한 작업, 실제로 실행한 검증, 남은 작업을 보고하고, 승인된 계획 범위 안에서 다음 단계를 계속 진행한다.

## 작업 절차

1. AGENTS.md와 구현 계획을 확인한다.
2. 계획에 작성된 작업을 순서대로 구현한다.
3. 각 단계가 끝나면 정상적으로 구현되었는지 확인한다.
4. 문제가 발견되면 원인을 확인하고 수정한다.
5. 각 단계가 끝나면 **단계별 보고**를 작성하고, 다음 단계를 계속 진행한다.
6. 모든 단계가 끝나면 전체 결과를 확인하고, **작업 결과 형식**으로 정리한다.

## 구현 상태와 검증 상태

단계별 보고에서는 **구현 상태**와 **검증 상태**를 반드시 따로 표시한다. 코드를 작성한 것과 그 코드가 올바르게 동작함을 확인한 것은 별개다.

| 구현 상태 | 기준 |
|---|---|
| 완료 | 계획된 작업을 모두 작성했다. |
| 부분 완료 | 일부만 작성했다. 무엇이 남았는지 적는다. |
| 보류 | 계획 변경 확인이나 외부 요인 때문에 진행하지 못했다. |

| 검증 상태 | 기준 |
|---|---|
| 통과 | 검증을 **실제로 실행했고** 기대한 결과가 나왔다. |
| 실패 | 검증을 실행했고 기대한 결과가 나오지 않았다. |
| 부분 실행 | 계획된 검증 중 일부만 실행했다. 실행한 것과 하지 못한 것을 나눠 적는다. |
| 미실행 | 검증을 실행하지 못했다. 이유를 적는다. |

검증 보고 규칙:
- **실행하지 않은 검증을 통과로 보고하지 않는다.** "통과할 것으로 보인다", "문제없을 것이다" 같은 추정은 검증 결과가 아니다.
- 코드를 읽고 판단한 것은 "코드 검토로 확인"이라고 명시하고, 실행 검증과 구분한다.
- 실행한 명령, 테스트 이름, 확인한 동작 등 검증 방법을 구체적으로 적는다.
- 사용자가 직접 해야 하는 검증(실기기 테스트, 에디터에서의 수동 확인 등)은 미실행으로 두고, 사용자가 확인할 방법을 적는다.

## 단계별 보고

각 단계가 끝나면 아래 형식으로 보고한다.

```markdown
## [단계 N/전체 M] <단계 이름>

**구현 상태**: 완료 / 부분 완료 / 보류
**검증 상태**: 통과 / 실패 / 부분 실행 / 미실행

### 완료한 작업
- <실제로 한 작업>

### 변경 파일
- 추가: <경로> — <내용>
- 수정: <경로> — <내용>
- 삭제: <경로> — <이유>

### 실행한 검증
- <검증 방법> → <결과>

### 실행하지 못했거나 추가 확인이 필요한 검증
- <검증 내용> — <실행하지 못한 이유 또는 확인이 필요한 이유>, <확인 방법>
(없으면 "없음")

### 남은 단계
- [ ] 단계 N+1: <이름>
- [ ] 단계 N+2: <이름>
- ...

### 다음 작업
단계 N+1: <이번에 바로 진행할 구체적인 작업>
```

보고 규칙:
- 완료한 작업과 변경 파일은 **실제로 변경한 내용만** 적는다. 계획에 있었지만 하지 않은 작업은 적지 않는다.
- 계획과 다르게 구현한 부분이 있으면 완료한 작업에 그 차이와 이유를 적는다.
- 남은 단계에는 계획의 남은 단계를 모두 적는다. 이전 단계에서 부분 완료나 미실행 검증으로 남은 일이 있으면 함께 적는다.

## 보고 후 진행

- 단계별 보고를 마친 뒤에는 사용자의 지시를 기다리지 않고, **승인된 계획 범위 안의 다음 단계를 계속 진행한다.**
- 다음 경우에는 진행을 멈추고, 이유를 설명한 뒤 사용자에게 확인받는다.
  - 계획을 변경해야 할 때 (단계 추가·삭제·순서 변경, 수정 대상 변경, 요구사항 해석 변경)
  - 검증이 실패했고, 원인을 수정하려면 계획 범위를 벗어나야 할 때
  - 실패하거나 실행하지 못한 검증 결과에 다음 단계가 직접 의존해서, 그대로 진행하면 이후 작업이 무의미해질 수 있을 때
- 검증 실패의 원인을 계획 범위 안에서 수정할 수 있으면 수정하고 다시 검증한 뒤, 그 과정을 단계별 보고에 적는다.
- 검증을 실행하지 못했지만 다음 단계가 그 결과에 의존하지 않으면 계속 진행하고, 미실행 검증으로 기록해 둔다.

## 작업 결과 형식

모든 단계가 끝나면 단계별 보고를 바탕으로 전체 결과를 정리한다.

### 구현 완료 내용
어떤 기능을 구현했는지 설명한다.
단계별 구현 상태를 요약한다. (예: 단계 1~4 완료, 단계 5 부분 완료)
계획과 다르게 구현한 부분이 있으면 함께 적는다.

### 검증 결과
어떤 방법으로 확인했고 결과가 어땠는지 설명한다.
실제로 실행한 검증과, 코드 검토로만 확인한 내용을 구분한다.

### 남은 문제
해결하지 못한 문제나 추가 확인이 필요한 사항을 설명한다.
모든 단계에서 나온 미실행·부분 실행·실패 검증을 빠짐없이 모으고, 사용자가 확인할 방법을 함께 적는다.

## 규칙

- 기존 계획의 범위 안에서 작업한다.
- 계획에 없는 기능은 임의로 추가하지 않는다.
- 기존 기능이 정상적으로 유지되도록 한다.
- 계획을 변경해야 한다면 이유를 설명하고 사용자에게 확인한다.
- 별도 요청 없이 Git Commit을 수행하지 않는다.
- 각 단계가 끝날 때마다 단계별 보고를 작성한다.
- 구현 상태와 검증 상태를 구분해서 보고한다.
- 실행하지 않은 검증을 통과한 것처럼 보고하지 않는다.
