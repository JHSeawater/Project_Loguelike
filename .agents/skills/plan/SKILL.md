# Plan

사용자가 요청한 기능을 구현하기 전에, 코드를 근거로 한 구현 계획을 작성한다.
이 스킬의 결과물은 **계획서**이며, 코드 변경은 포함하지 않는다.

## 핵심 원칙

- **근거 우선**: 모든 판단은 실제로 확인한 코드·문서에 기반한다. 확인한 내용에는 파일 경로(가능하면 심볼 이름)를 붙인다.
- **확인과 추정의 구분**: 확인하지 못한 내용은 `[추정]`으로 표시하고, 왜 그렇게 판단했는지 한 줄로 적는다.
- **규모에 맞는 깊이**: 작업 규모에 따라 분석 깊이를 조절한다. 작은 수정에 모든 절차를 적용하지 않는다.
- **범위 고정**: 요청 범위를 넘는 개선은 제안으로만 남기고 계획에 섞지 않는다.

## 0. 작업 규모 판단

먼저 요청의 규모를 판단하고, 계획서 첫머리에 명시한다.

| 규모 | 기준 (참고) | 적용할 절차 |
|---|---|---|
| 소 | 1~2개 파일, 기존 동작 변경 없음 | 1, 2(간략), 6, 7(간략), 8, 계획서 축약형 |
| 중 | 여러 파일, 기존 기능과 연결됨 | 1~8 전체 |
| 대 | 새 시스템/구조 변경, 다수 기능에 영향 | 1~8 전체 + 단계별 중간 검증 지점 명시 |

판단이 애매하면 한 단계 큰 쪽으로 본다.

## 1. 컨텍스트 조사

1. `AGENTS.md`(없으면 `README`, `CONTRIBUTING`, 프로젝트 설정 파일)를 읽고 코딩 규칙, 아키텍처, 금지 사항을 확인한다. 루트 지침에 분야별 연결표가 있으면 그 표로 관련 분야 지침과 테스트를 찾아 함께 읽는다.
2. 요청과 관련된 진입점(호출 시작점, 화면, 이벤트, API 등)을 찾는다.
3. 프로젝트의 기존 패턴을 파악한다: 폴더 구조, 네이밍 규칙, 상태 관리 방식, 에러 처리 방식, 테스트 방식.
4. 기준 커밋(`git rev-parse --short HEAD`)과 기존 미커밋 변경(`git status`)을 확인해 계획서에 적는다.

이 단계에서 문서가 없거나 규칙이 서로 충돌하면 그 사실을 계획서에 기록한다.

## 2. 요구사항 분석

### 2-1. 요구사항 정리
사용자의 요청을 **검증 가능한 문장**으로 다시 쓴다.
- 나쁜 예: "인벤토리를 개선한다"
- 좋은 예: "아이템이 최대 수량(N)에 도달하면 획득을 거부하고 알림을 표시한다"

### 2-2. 모호성 탐지
아래 신호가 보이면 모호한 요구사항으로 분류한다.
- 해석이 둘 이상 가능한 표현 ("적당히", "자연스럽게", "빠르게", "등")
- 주체·대상·시점이 빠진 문장 ("저장된다" → 언제? 어디에?)
- 기존 동작과 충돌하는 요구
- 수치·조건이 정해지지 않은 요구

각 모호성마다 **가능한 해석들**과 **채택할 기본 가정**을 함께 제시한다.

### 2-3. 누락된 요구사항 탐색
사용자가 말하지 않았지만 구현 시 반드시 결정해야 하는 항목을 찾는다. 해당하는 항목만 다룬다.

- **입력/경계값**: 0, 음수, 최대값, 빈 값, null, 매우 큰 입력, 중복 입력
- **실패 조건**: 리소스 없음, 저장/로드 실패, 네트워크 실패, 타임아웃, 권한 없음
- **상태**: 초기 상태, 중간에 취소/중단, 재진입, 연속 호출, 동시에 발생하는 이벤트
- **데이터**: 기존 저장 데이터와의 호환, 마이그레이션, 되돌리기
- **사용자 경험**: 실패 시 피드백, 로딩 중 표시, 접근성
- **비기능**: 성능 한계, 메모리, 플랫폼별 차이, 다국어

### 2-4. 질문 작성
질문은 다음 규칙을 따른다.
- **차단 질문**(답 없이는 설계가 갈리는 것)과 **비차단 질문**(기본 가정으로 진행 가능한 것)을 구분한다.
- 질문마다 선택지와 추천안을 함께 제시해 사용자가 빠르게 답할 수 있게 한다.
- 한 번에 최대 5개까지만 묻고, 중요도 순으로 정렬한다.
- 차단 질문이 있으면 해당 부분의 구현 단계는 "결정 대기"로 표시한다.

## 3. 기존 구현 재사용 탐색

새로 만들기 전에 프로젝트 안에 이미 있는 것을 찾는다.

1. **검색 키워드를 여러 개 만든다**: 기능명, 동의어, 영문/한글 표현, 프로젝트 네이밍 규칙에 맞는 이름 (예: `Manager`, `Service`, `Util`, `Helper`, `Controller`, `System`).
2. **찾을 대상**: 유사 기능, 공용 유틸리티, 매니저/싱글톤, 베이스 클래스, 이벤트 시스템, 설정·데이터 정의, 외부 라이브러리.
3. **후보별로 판단한다**:
   - 그대로 재사용 / 확장해서 재사용 / 재사용 불가(이유 명시)
4. 비슷한 기능이 이미 여러 곳에 중복되어 있다면 기술 부채로 기록한다(5단계).

찾지 못했다면 "검색한 키워드와 범위"를 남겨 재확인할 수 있게 한다.

## 4. 영향 범위 분석

수정 대상 파일만이 아니라 그 주변까지 조사한다.

- **호출 관계**: 수정할 함수/클래스를 누가 호출하는가? 무엇을 호출하는가?
- **의존성**: 공유 상태, 전역 객체, 이벤트 구독자, 인터페이스 구현체
- **데이터**: 직렬화된 데이터, 저장 파일, 설정 파일, 에디터/씬/프리팹 등에 연결된 참조
- **연관 기능**: 같은 데이터나 시스템을 쓰는 다른 기능
- **테스트·문서**: 수정이 필요한 기존 테스트, 갱신이 필요한 문서

영향도는 **높음 / 중간 / 낮음**으로 표시하고, "높음"은 반드시 검증 방법에 반영한다.

## 5. 기술 부채 탐지

구현에 **실제로 영향을 주는** 기존 코드의 구조적 문제만 기록한다. 일반적인 코드 리뷰는 하지 않는다.

- 예: 과도한 결합, 중복 로직, 거대 클래스, 하드코딩된 값, 테스트 불가능한 구조, 일관성 없는 패턴
- 각 항목마다 다음을 적는다.
  - 위치(파일/심볼)
  - 이번 구현에 주는 영향
  - 대응 방향: **이번에 함께 처리 필요** / **우회 가능, 별도 작업 권장** / **영향 미미, 기록만**
- "이번에 함께 처리 필요"인 경우에만 구현 단계에 포함하고, 나머지는 범위 밖으로 둔다.

## 6. 작업 단계 세분화

큰 기능을 독립적으로 구현하고 검증할 수 있는 작은 단계로 나눈다.

각 단계는 다음을 만족해야 한다.
- **독립 검증 가능**: 단계가 끝나면 그 결과만으로 확인할 수 있다.
- **안정 상태 유지**: 단계가 끝날 때마다 프로젝트가 빌드/실행 가능한 상태여야 한다.
- **작은 크기**: 한 단계는 하나의 목적만 가진다. 설명에 "그리고"가 여러 번 들어가면 나눈다.
- **의존 순서**: 기반(데이터·인터페이스) → 핵심 로직 → 연결(UI·이벤트) → 예외 처리 → 정리 순서를 기본으로 한다.

각 단계에는 **관련 요구사항 ID**와 **완료 조건**을 한 줄로 적는다. 모든 요구사항은 적어도 하나의 단계와 하나의 검증 방법에 연결되어야 한다.

## 7. 위험 요소 정리

앞 단계의 결과를 바탕으로 구현 중 또는 구현 후에 문제가 될 수 있는 요소를 정리한다.

- **출처별로 확인한다**:
  - 2단계: 결정되지 않은 요구사항, 기본 가정이 틀렸을 경우
  - 4단계: 영향도 "높음" 항목의 회귀 가능성
  - 5단계: 우회하기로 한 기술 부채가 구현을 방해할 가능성
  - 6단계: 순서상 되돌리기 어렵거나 검증이 늦게 가능한 단계
  - 기타: 처음 쓰는 라이브러리·API, 성능, 플랫폼 차이, 데이터 손실 가능성
- 각 위험마다 **가능성(높음/중간/낮음)**, **영향(높음/중간/낮음)**, **대응 방법**(예방책 또는 발생 시 조치)을 적는다.
- 가능성과 영향이 모두 낮은 위험은 생략할 수 있다.

## 8. 계획 제시 및 대기

1. 아래 형식에 맞춰 계획서를 작성해 사용자에게 보여준다.
2. 차단 질문이 남아 있으면 계획서 맨 위에 그 사실과 질문을 먼저 제시한다.
3. 계획을 보여준 뒤에는 구현을 시작하지 않고 사용자의 다음 지시(승인, 수정 요청, 질문에 대한 답변)를 기다린다.
4. 계획서를 파일로 저장할 때는 루트 지침의 구현 계획서 규칙(상태·기준 커밋·대체 문서)을 따르고, 사용자가 승인하면 상태를 '승인'으로 바꾼다.

## 계획서 형식

```markdown
# 계획: <기능 이름>

**규모**: 소 / 중 / 대 — <판단 이유 한 줄>
**상태**: 초안 · **기준 커밋**: <짧은 해시> · **기존 미커밋 변경**: <파일 목록 또는 없음>

## 목표
무엇을, 왜 구현하는가?

## 요구사항
어떤 동작을 만족해야 하는가?
- [ ] R1. <검증 가능한 문장>
- [ ] R2. ...

## 확인이 필요한 사항
### 차단 질문
1. <질문> — 선택지: A / B (추천: A, 이유)
### 비차단 질문 (기본 가정으로 진행)
1. <질문> — 기본 가정: <가정>

## 누락 가능성이 있는 요구사항
| 항목 | 상황 | 제안 동작 |
|---|---|---|

## 재사용 가능한 기존 구현
| 후보 | 위치 | 판단 | 비고 |
|---|---|---|---|

## 영향 범위
| 대상 | 관계 | 영향도 | 비고 |
|---|---|---|---|

## 수정 대상
어떤 파일을 추가하거나 수정해야 하는가?
- 추가: <경로> — <역할>
- 수정: <경로> — <변경 내용>

## 구현 단계
어떤 순서로 작업할 것인가?
1. <단계> — 요구사항: R1 · 완료 조건: <조건>
2. ...

## 검증 방법
구현 결과를 어떻게 확인할 것인가?
- 요구사항별 확인 방법 (R1 → 단계 번호 → 테스트 파일·명령 또는 화면 확인 절차)
- 영향도 "높음" 항목의 회귀 확인 방법
- 경계값·실패 조건 확인 방법

## 위험 요소
구현 중 또는 구현 후에 무엇이 문제가 될 수 있는가?
| 위험 | 가능성 | 영향 | 대응 |
|---|---|---|---|

## 기술 부채 (별도 보고)
| 위치 | 문제 | 이번 구현에 주는 영향 | 대응 방향 |
|---|---|---|---|

## 범위 밖
이번 작업에서 하지 않는 것과 그 이유.
```

**소 규모**일 때는 목표 / 요구사항 / 수정 대상 / 구현 단계 / 검증 방법만 작성하고, 해당 사항이 있는 경우에만 나머지 섹션을 추가한다. 내용이 없는 섹션은 "해당 없음"으로 적거나 생략한다.

## 규칙

- 계획 단계에서는 코드와 설정 파일을 변경하지 않는다. 읽기, 검색, 빌드·테스트 실행으로 현재 상태를 확인하는 것은 허용한다.
- 확인하지 않은 내용을 사실처럼 작성하지 않는다. 추정은 `[추정]`으로 표시한다.
- 요구사항이 불명확하면 가정을 명시하거나 질문한다. 차단 질문이 남아 있으면 그 사실을 계획서 맨 위에 알린다.
- 요청 범위를 넘는 리팩터링·개선은 "기술 부채" 또는 "범위 밖"에만 적는다.
- 계획을 작성한 뒤 사용자의 다음 지시를 기다린다. 사용자가 승인하기 전에는 구현을 시작하지 않는다.
- 사용자가 계획을 수정하면 변경된 부분만 갱신하고, 무엇이 바뀌었는지 짧게 알린다.
