# Review Plan

작성된 구현 계획을 검토하고 개선할 부분을 제안한다.
특히 사용자의 원래 요청이 계획에 빠짐없이 반영되었는지 항목별로 추적하고, 빠진 내용이 있으면 무엇이 빠졌는지와 계획을 어떻게 보완하면 좋을지 제안한다.

## 작업 절차

1. 검토할 계획서와 AGENTS.md를 확인한다.
2. 계획과 관련된 기존 코드를 확인한다.
3. 요구사항이 계획에 빠짐없이 반영되었는지 검토한다. → 아래 **요구사항 반영 점검** 절차를 따른다.
4. 기존 기능에 미치는 영향과 예상 위험을 검토한다.
5. 구현 단계와 검증 방법이 적절한지 확인한다.
6. 발견한 문제와 개선안을 정리한다.

## 요구사항 반영 점검 (3단계 세부 절차)

### 3-1. 원래 요청 확보

검토 기준이 될 **원래 사용자 요청**을 찾는다. 다음 순서로 확인한다.

1. 현재 대화에서 사용자가 제공한 요청 원문
2. 사용자가 지정한 이슈, 문서, 메모
3. 계획서 안에 인용되거나 요약된 요청

계획서의 "요구사항" 섹션만 있고 원래 요청을 확인할 수 없는 경우:
- 계획서의 요구사항을 기준으로 삼되, **원래 요청과 대조하지 못했다는 사실**을 검토 결과 맨 위에 밝힌다.
- 이 경우 "누락"이라는 판정은 사용하지 않는다. 원래 요청에 없던 것인지, 계획에서 빠진 것인지 구분할 수 없기 때문이다.

원래 요청을 전혀 확인할 수 없으면 사용자에게 요청 원문을 질문하고, 3단계를 제외한 나머지 검토만 진행한다.

### 3-2. 요구사항 항목 분해

원래 요청을 **확인 가능한 요구사항 항목**으로 나눈다.

- 한 항목에는 하나의 동작이나 조건만 담는다. "A하고 B한다"는 두 항목으로 나눈다.
- 각 항목에 `Q1`, `Q2`… 형식으로 번호를 붙인다. (계획서의 `R1` 번호와 구분하기 위해 별도 번호를 쓴다.)
- 각 항목 옆에 **근거가 된 요청 원문의 해당 부분**을 짧게 적는다.
- 요청에 명시되지 않은 내용은 요구사항 항목으로 만들지 않는다. 해석이 필요한 표현은 원문 그대로 항목화하고, 해석이 갈리는 점은 3-3의 판단 근거에 적는다.
- 요청에 "예시", "참고", "가능하면"처럼 필수가 아님을 나타내는 표현이 있으면 항목에 `(선택)`으로 표시한다.

### 3-3. 계획 반영 위치 추적과 판정

각 요구사항 항목이 계획서의 어느 부분에 반영되었는지 찾는다. 요구사항 섹션만 보지 말고 수정 대상, 구현 단계, 검증 방법 등 계획서 전체를 확인한다.

항목마다 아래 네 가지 중 하나로 판정한다.

| 판정 | 기준 |
|---|---|
| **반영** | 계획의 구현 단계(또는 수정 대상)에 해당 동작이 구체적으로 포함되어 있다. |
| **부분 반영** | 관련 내용은 있지만 일부 조건·대상·경우가 빠졌거나, 요청보다 좁게 해석되었다. |
| **누락** | 원래 요청에 분명히 있는데 계획 어디에도 대응하는 내용이 없다. |
| **판단 불가** | 요청이 모호하거나, 원래 요청을 확인할 수 없거나, 계획의 표현만으로 반영 여부를 판단할 수 없다. |

판정 규칙:
- **누락은 원래 요청을 확인했고, 그 요청에 해당 내용이 분명히 있을 때만** 사용한다. 자료가 부족하면 판단 불가로 둔다.
- 계획의 다른 표현이 같은 의미일 가능성이 있으면 누락이 아니라 부분 반영이나 판단 불가로 두고, 그 이유를 적는다.
- 항목마다 **판단 근거**를 남긴다. 요청 원문의 해당 부분과 계획서의 해당 위치(섹션명, 단계 번호)를 함께 적는다.
- 반영이 아닌 항목에는 **계획 보완안**을 적는다. 어느 섹션의 어느 위치에 무엇을 추가하거나 고치면 되는지 구체적으로 제안한다.

### 3-4. 검증 누락 확인

3-3의 판정과 별개로, 각 항목에 대응하는 **검증 방법**이 계획에 있는지 확인한다.

| 검증 상태 | 기준 |
|---|---|
| **있음** | 해당 요구사항을 확인하는 검증 방법이 계획에 있다. |
| **검증 누락** | 구현 단계에는 반영되어 있지만, 이를 확인하는 검증 방법이 없다. |
| **해당 없음** | 구현 자체가 누락·판단 불가라서 검증 여부를 따질 수 없다. |

"반영 + 검증 누락"인 항목은 별도로 모아 보고한다. 구현은 계획되어 있어도 완료 여부를 확인할 수 없기 때문이다. 이 항목에는 추가할 검증 방법을 제안한다.

### 3-5. 요청 밖 항목 구분

- 검토 중 사용자가 요청하지 않았지만 고려할 만한 내용(예외 상황, 경계값, 개선점 등)을 발견하면 **필수 요구사항으로 추가하지 않는다.**
- 이런 내용은 "참고 제안"으로 따로 적고, 필수가 아님을 분명히 한다.
- 반대로 계획에 원래 요청과 연결되지 않는 작업이 있으면 문제로 단정하지 말고, 요청 범위와의 관계를 확인해 보라고 참고로만 알린다.

## 검토 결과 형식

```markdown
# 계획 검토: <계획 이름>

> (원래 요청을 확인하지 못했거나 일부만 확인한 경우 여기에 먼저 밝힌다.)

## 종합 평가
계획의 전반적인 상태를 간단히 설명한다.
요구사항 반영 현황: 반영 N / 부분 반영 N / 누락 N / 판단 불가 N, 검증 누락 N

## 요구사항 반영 점검
| ID | 요구사항 | 요청 근거 | 계획 반영 위치 | 판정 | 검증 |
|---|---|---|---|---|---|
| Q1 | ... | "..." | 구현 단계 2 | 반영 | 있음 |
| Q2 | ... | "..." | 구현 단계 3 | 부분 반영 | 검증 누락 |
| Q3 | ... | "..." | 없음 | 누락 | 해당 없음 |

### 항목별 판단 근거와 보완안
반영이 아니거나 검증 누락인 항목만 적는다.
- **Q2 (부분 반영, 검증 누락)**
  - 판단 근거: 요청은 ~이지만 계획 구현 단계 3은 ~만 다룬다.
  - 계획 보완안: 구현 단계 3에 ~를 추가하고, 검증 방법에 ~를 추가한다.
- **Q3 (누락)**
  - 판단 근거: ...
  - 계획 보완안: ...

### 검증 누락 항목
구현 단계에는 있지만 검증 방법이 없는 항목과 추가할 검증 방법.

### 판단 불가 항목
판단할 수 없는 이유와, 판단에 필요한 정보(사용자에게 확인할 질문).

## 발견한 문제
요구사항 반영 점검 결과와 영향·위험·구현 단계·검증 방법 검토 결과를 함께 정리한다.
- 문제 내용
- 문제가 발생할 수 있는 이유
- 중요도: 높음 / 보통 / 낮음

## 개선 제안
발견한 문제를 어떻게 해결하면 좋을지 설명한다.

## 참고 제안 (필수 아님)
요청에는 없지만 고려할 만한 내용. 반영 여부는 사용자가 결정한다.

## 최종 의견
계획을 그대로 진행해도 되는지, 수정이 필요한지 판단한다.
```

### 최종 의견 판단 기준

- **진행 가능**: 필수 요구사항이 모두 반영이고, 중요도 높음 문제가 없다.
- **수정 후 진행**: 필수 요구사항 중 누락·부분 반영·검증 누락이 있거나, 중요도 높음 문제가 있다.
- **확인 후 판단**: 판단 불가 항목이 핵심 요구사항에 해당하거나, 원래 요청을 확인하지 못했다.

`(선택)` 항목의 누락은 그것만으로 "수정 후 진행" 판정의 근거가 되지 않는다.

내용이 없는 섹션은 "해당 없음"으로 적는다. 문제가 없으면 문제가 없다고 명확하게 쓴다.

## 규칙

- 계획 검토 단계에서는 코드를 수정하지 않는다.
- 검토 대상 계획서도 임의로 수정하지 않는다. 보완안은 제안으로만 제시한다.
- 실제 코드와 요구사항에 근거해 검토한다.
- 근거 없는 문제를 만들어내지 않는다.
- 문제가 없다면 문제가 없다고 명확하게 설명한다.
- 원래 요청이 없거나 자료가 부족하면 누락으로 단정하지 않고 판단 불가로 둔다.
- 사용자가 요청하지 않은 기능은 필수 요구사항으로 추가하지 않는다. 필요하면 참고 제안으로만 적는다.
- 판정마다 요청 원문과 계획서 위치를 근거로 남긴다.
- 검토가 끝나면 사용자의 다음 지시를 기다린다.
